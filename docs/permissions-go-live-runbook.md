# دليل إطلاق نظام صلاحيات Almdina والرجوع الآمن

هذا الدليل مخصص لنقل نظام الصلاحيات الجديد من `Develop` إلى بيئة الاختبار ثم الإنتاج. لا تُمنح أي صلاحيات أعمال تلقائيًا، ولا يُنشئ الاستيراد أدوارًا جديدة.

## 1. شروط البدء

- نجاح `Static Checks` و`Frappe v16 Integration` على رأس الـPR نفسه.
- بقاء الـPR في وضع Draft إلى أن ينتهي اختبار المستخدمين في بيئة `Develop`.
- معرفة اسم الموقع المستهدف ومسار مشروع Docker قبل تنفيذ أي أمر.
- وجود مستخدم طوارئ موثوق يستطيع الدخول وإدارة الصلاحيات.
- عدم إجراء تغييرات يدوية متزامنة على Role Permission Manager أثناء الترحيل.

## 2. النسخة الاحتياطية قبل التحديث

نفّذ النسخة الاحتياطية من داخل Bench الخاص بالموقع المستهدف:

```bash
bench --site <site-name> backup --with-files
```

تحقق من وجود الملفات الجديدة داخل:

```text
sites/<site-name>/private/backups/
```

انسخ النسخة إلى مسار خارج حاويات المشروع أو إلى مخزن نسخ احتياطي مستقل. لا تتابع إن لم تكن قاعدة البيانات والملفات متوفرة وقابلة للاستعادة.

## 3. تصدير مصفوفة الصلاحيات الحالية

من جلسة Frappe موثوقة استدعِ:

```python
from almdina_erp.almdina_erp.services.permission_management_service import export_permission_bundle
bundle = export_permission_bundle()
```

احفظ JSON الناتج خارج الموقع. الحزمة تحتوي الأدوار والصلاحيات فقط، ولا تحتوي مستخدمين أو كلمات مرور أو Audit.

يمكن أيضًا تصدير دور واحد من صفحة:

```text
/app/factory-permissions
```

## 4. تجربة التحديث على Develop

حدّث بيئة الاختبار فقط من فرع `Develop` بالطريقة المعتمدة للمشروع، ثم نفّذ:

```bash
bench --site <develop-site> migrate
bench --site <develop-site> clear-cache
```

في بنية Almdina الحالية يمكن استخدام سكربت التحديث المعتمد بعد دمج الـPR في `Develop`:

```bash
update-almdina
```

تحقق بعد التحديث من أن صورة Docker والحاويات والموقع تعكس Commit المتوقع، ولا تعتمد على نجاح الأمر وحده.

## 5. فحوص المستخدمين الأساسية

أنشئ أدوار اختبار بأسماء جديدة ولا تستخدم أسماء الأدوار التاريخية لإثبات الصلاحية.

### إدخال الطلبات

- إنشاء طلب وتعديل المسودة.
- إرسال الطلب للمراجعة.
- طباعة القياسات وفاتورة الزبون.
- التأكد من عدم ظهور التكلفة الداخلية أو الإنتاج أو إدارة الصلاحيات.

### التخطيط والرسم

- فتح خطة القص والرسم.
- حساب الخطة ورفع أو استبدال DXF حسب الصلاحية.
- اعتماد الخطة فقط عند منح `approve_dxf`.
- التأكد من عدم ظهور التكلفة والتقارير المالية.

### عامل الإنتاج

- ظهور الطلبات المسندة له فقط.
- بدء وتسليم مرحلته الحالية.
- رفض تنفيذ مرحلة مسندة لعامل آخر.
- عدم ظهور الإرسال للإنتاج أو الرجوع أو إعادة الإسناد.

### مشرف الإنتاج

- الإرسال للإنتاج والرجوع وإعادة الإسناد والتسليم النهائي.
- عرض التقرير التشغيلي دون الأعمدة المالية.
- عدم ظهور إعدادات المستخدمين أو الصلاحيات ما لم تُمنح صراحة.

### التسعير والمستندات

- عرض وتعديل التكلفة حسب المنح.
- اعتماد الأسعار الخاصة.
- طباعة التقرير الداخلي فقط عند منح صلاحياته.
- التأكد من عدم القدرة على تنفيذ مراحل الإنتاج.

### إدارة المعمل

- إدارة المستخدمين والإعدادات والمسارات والقشاط والصلاحيات.
- التأكد من عدم امتلاك اعتماد الطلبات أو الإنتاج أو التقارير المالية تلقائيًا.

## 6. اختبار الروابط المباشرة والـAPI

لا يكفي إخفاء الأزرار. جرّب فتح الروابط واستدعاء APIs بحساب غير مخول:

- الطلب وخطة القص ومرحلة الإنتاج وقطعة التعويض.
- صفحات التكلفة والتقارير والإعدادات والمستخدمين.
- تنزيل DXF والمرفقات والطباعة.
- endpoints القديمة في `cutting_plan_service` و`shop_floor_service`.

يجب أن تُرفض العمليات على الخادم حتى عند معرفة الرابط أو اسم الدالة.

## 7. استيراد مصفوفة كاملة

عاين الحزمة أولًا:

```python
from almdina_erp.almdina_erp.services.permission_management_service import preview_permission_bundle_import
preview = preview_permission_bundle_import(bundle)
```

راجع:

- `role_count`
- `changed_role_count`
- `change_count`
- `critical_change_count`
- `requires_self_lockout_confirmation`

الاستيراد لا ينشئ Role مفقودًا. وجود دور واحد غير موجود يلغي العملية كاملة قبل أي كتابة.

بعد المراجعة:

```python
from almdina_erp.almdina_erp.services.permission_management_service import import_permission_bundle
result = import_permission_bundle(
    bundle,
    confirm_sensitive=1,
    confirm_self_lockout=0,
)
```

لا تستخدم `confirm_self_lockout=1` إلا في تغيير مقصود ومراجع يزيل آخر صلاحية لإدارة المصفوفة.

## 8. المراقبة بعد الإطلاق

راجع السجلات التالية:

- `Almdina Permission Audit`
- `Almdina User Audit`
- `Almdina Master Data Audit`

وتحقق من:

- عدم وجود Grant غير متوقع.
- عدم وجود كلمات مرور في Audit.
- مصدر التغييرات المستوردة هو `Almdina Permission Import`.
- عدم ظهور أخطاء Permission متكررة بسبب دور ناقص.
- عدم وجود بيانات مالية في Responses لمستخدم تشغيلي.

## 9. شروط إيقاف الإطلاق

أوقف التحديث ولا تدمج إلى `main` عند حدوث أي مما يلي:

- فشل `migrate` أو اختلاف المخطط.
- عدم قدرة مستخدم الطوارئ على إدارة الصلاحيات.
- ظهور بيانات تكلفة أو تقارير مالية لمستخدم غير مخول.
- قدرة مستخدم غير مسند على تشغيل مرحلة إنتاج.
- اختلاف عدد الأدوار أو الصلاحيات عن Preview المعتمد.
- فشل فتح الطلبات الحالية أو الخطط المعتمدة أو ملفات DXF.

## 10. الرجوع

1. أوقف الكتابة على الموقع مؤقتًا.
2. أعد صورة التطبيق أو Commit السابق المعتمد.
3. استعد نسخة قاعدة البيانات والملفات المأخوذة قبل التحديث.
4. شغّل الحاويات بالإصدار السابق.
5. نفّذ `clear-cache` وتحقق من التطبيقات المثبتة.
6. اختبر تسجيل الدخول وطلبًا قائمًا وخطة قص ومرحلة إنتاج.
7. لا تستورد حزمة صلاحيات جديدة فوق قاعدة بيانات قديمة إلا بعد التأكد من توافق إصدار الحزمة.

مثال استعادة Frappe، بعد اختيار ملفات النسخة الصحيحة:

```bash
bench --site <site-name> restore <database-backup.sql.gz> \
  --with-public-files <public-files.tar> \
  --with-private-files <private-files.tar>
bench --site <site-name> clear-cache
```

تختلف أسماء الملفات ومسارات Docker حسب البيئة؛ استخدم النسخة التي تم التحقق منها في الخطوة الثانية.

## 11. قرار الدمج

يُحوّل الـPR من Draft إلى Ready فقط بعد:

- نجاح CI على الرأس النهائي.
- نجاح تجربة `Develop` ببيانات مماثلة للإنتاج.
- توقيع نتائج اختبار الشخصيات الست.
- التحقق من النسخة الاحتياطية وخطة الرجوع.
- عدم وجود Review Threads أمنية مفتوحة.

بعد الاختبار الفعلي فقط يُدمج إلى الفرع المطلوب وفق سياسة المشروع.

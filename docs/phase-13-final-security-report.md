# تقرير المرحلة الثالثة عشرة: الإغلاق الأمني وقابلية النقل والإطلاق

## الهدف

إغلاق مشروع الصلاحيات على مستوى المعمارية والخادم والواجهة، والتأكد من أن الصلاحيات قابلة للإدارة والنقل والاختبار دون الاعتماد على أسماء أدوار أعمال ثابتة أو منح تلقائية خفية.

## نتيجة مراجعة الكود

### 1. حدود التفويض

- جميع الخدمات النشطة الحساسة تستخدم Business Capabilities أو صلاحيات Frappe القياسية.
- فحوص أسماء الأدوار الثابتة ممنوعة في واجهات JavaScript المحملة وفي الخدمات الأساسية.
- أي endpoint قديم ما زال يحتوي منطق Role قديم يجب أن يكون محولًا عبر `override_whitelisted_methods` إلى خدمة محمية.
- الوحدات الخارجة عن نطاق المنتج الحالي مغلقة Fail Closed ولا تحمل واجهاتها القديمة.

الاختبار المرجعي:

```text
almdina_erp/tests/test_final_security_architecture.py
```

### 2. قوالب الصلاحيات

توجد قوالب اختيارية لأكثر الشخصيات شيوعًا:

- إدخال الطلبات.
- التخطيط والرسم.
- عامل الإنتاج.
- مشرف الإنتاج.
- التسعير والمستندات.
- مركز التحكم والجودة.
- إدارة المعمل.

القوالب لا تنشئ Roles ولا تحفظ صلاحيات تلقائيًا. يتم عرض Preview كامل قبل الحفظ، وتبقى المصفوفة الفعلية تحت تحكم المسؤول.

الملف المرجعي:

```text
almdina_erp/almdina_erp/application/security/permission_templates.py
```

### 3. قابلية نقل مصفوفة الصلاحيات

- تصدير دور واحد أو المصفوفة كاملة بصيغة JSON ذات Schema وVersion ثابتين.
- Checksum لمنع قبول ملف تم تعديله بعد التصدير.
- لا يتضمن التصدير مستخدمين أو كلمات مرور أو Sessions أو Audit Records.
- الاستيراد Preview-first ولا يكتب قبل التأكيد.
- الحزمة لا تنشئ Roles مفقودة؛ وجود Role غير موجود يلغي العملية كاملة قبل أي كتابة.
- التغييرات الحساسة والحرجة تحتاج تأكيدًا صريحًا.
- منع القفل الذاتي عند إزالة آخر صلاحية لإدارة المصفوفة إلا بتأكيد صريح.
- الحفظ متعدد الأدوار ذري، ويسجل Audit مستقلًا لكل Role متغير.

الخدمات المرجعية:

```text
export_role_permissions
export_permission_bundle
preview_permission_import
preview_permission_bundle_import
import_permission_bundle
```

### 4. اختبارات الشخصيات

تم تثبيت حدود كل شخصية آليًا:

- مدخل الطلبات لا يعتمد الطلب ولا يرى التكلفة الداخلية.
- المخطط والمصمم لا يملكان الإرسال أو إعادة الإسناد أو الصلاحيات المالية.
- العامل يبدأ ويسلم مرحلته المسندة فقط.
- المشرف يدير الإنتاج دون تكلفة مالية أو إدارة صلاحيات.
- مسؤول التسعير يدير المستندات المالية دون التحكم بالإنتاج.
- مركز التحكم والجودة لا يرى البيانات المالية.
- مدير المعمل يدير المستخدمين والإعدادات والبيانات الأساسية دون منح اعتماد أو تشغيل أو تقارير مالية تلقائيًا.

الاختبار المرجعي:

```text
almdina_erp/tests/test_permission_personas_e2e.py
```

### 5. Clean Architecture

- السياسات والقوالب وتحليل الأثر داخل Domain/Application ولا تستورد Frappe.
- التحقق من المستخدم الحالي وقراءة `Custom DocPerm` والحفظ والتدقيق محصور في Infrastructure/Services.
- واجهة الصلاحيات تعتمد Context الخادم ولا تقرأ `frappe.user_roles`.
- طبقات التوافق القديمة Facades صغيرة ولا تملك قواعد أعمال أو SQL أو Authorization خاصًا بها.

### 6. UI/UX

- القالب يعرض وصفًا ونطاقًا ومخاطر قبل التطبيق.
- الاستيراد يعرض عدد الأدوار والتغييرات والتغييرات الحرجة قبل الحفظ.
- لا يوجد حفظ تلقائي عند اختيار قالب أو ملف.
- حالات القفل الذاتي والتغييرات الحساسة لها تأكيدات منفصلة.
- واجهة عربية وتستخدم Shared Application Shell نفسها لجميع المستخدمين.

## الاختبارات الآلية المطلوبة لإغلاق المرحلة

يجب أن تكون جميع النتائج التالية خضراء على Commit واحد:

1. Static Checks.
2. Frappe v16 Integration.
3. Python وJSON وJavaScript syntax.
4. محاكاة المتصفح.
5. تثبيت Frappe وERPNext وAlmdina ERP من بيئة نظيفة.
6. تشغيل `migrate` مرتين.
7. جميع اختبارات التطبيق داخل Frappe.
8. اختبارات القوالب والشخصيات وقابلية النقل والإغلاق الأمني.
9. اختبار رفض Checksum غير الصحيح.
10. اختبار إلغاء استيراد الحزمة كاملة عند وجود Role مفقود.

## ما لا يمكن اعتماده آليًا فقط

تبقى النقاط التالية إلزامية على موقع `Develop` مستقل قبل تحويل الـPR من Draft:

- اختبار كل شخصية بحساب حقيقي وليس Administrator.
- اختبار الرابط المباشر وAPI والمرفقات والطباعة لكل شخصية.
- اختبار الموبايل والتمرير وحالات التحميل ورسائل الخطأ.
- اختبار نسخة من بيانات الإنتاج بعد نسخة احتياطية قابلة للاستعادة.
- اختبار خطة الرجوع فعليًا.
- موافقة المستخدم بعد الاختبار الوظيفي.

## قرار المرحلة

تعتبر المرحلة الثالثة عشرة مكتملة على مستوى الكود عندما تنجح البوابتان على الرأس النهائي. يبقى الـPR Draft ولا يتم الدمج إلى `Develop` أو `main` قبل تنفيذ قائمة الإطلاق اليدوية وموافقة المستخدم.

القائمة التشغيلية الكاملة:

```text
docs/permission-rollout-checklist.md
```

# قائمة إطلاق نظام الصلاحيات في Almdina ERP

هذه القائمة هي بوابة تشغيل إلزامية قبل تحويل Pull Request الصلاحيات من Draft أو دمجه في `Develop` ثم `main`.

## 1. نسخة احتياطية

- أخذ نسخة كاملة من قاعدة بيانات موقع الاختبار قبل الترقية.
- حفظ ملفات الموقع الخاصة والعامة مع النسخة.
- تسجيل اسم Image وCommit الحاليين قبل النشر.
- التحقق عمليًا من إمكانية قراءة النسخة الاحتياطية، وليس الاكتفاء بإنشائها.
- عدم تضمين كلمات المرور أو ملفات الأسرار داخل GitHub أو تقرير الاختبار.

## 2. بيئة Develop

- نشر الفرع على موقع اختبار مستقل فقط.
- تشغيل `migrate` مرتين للتأكد من Idempotency.
- تشغيل بناء الأصول وتنظيف Cache وفق مسار النشر المعتمد.
- لا يتم الدمج إلى `main` ولا تشغيل `update-almdina` على الإنتاج قبل قبول الاختبارات الوظيفية.
- التأكد أن موقع الاختبار لا يستخدم قاعدة بيانات الإنتاج ولا ملفاتها المشتركة.

## 3. اختبارات الشخصيات

اختبار كل شخصية بحساب مستقل ودور مستقل، وعدم استخدام Administrator للتحقق الوظيفي:

- مدخل طلبات: إنشاء وتعديل وإرسال الطلب، دون اعتماد أو تكلفة داخلية.
- مخطط/مصمم: خطة القص والرسم وDXF، دون صلاحيات مالية أو إدارة مستخدمين.
- عامل إنتاج: بدء وتسليم مرحلته المسندة فقط، دون إرسال الطلب أو إعادة إسناد العامل.
- مشرف إنتاج: إرسال وإعادة إسناد ورجوع وتسليم، دون اعتماد الطلب أو عرض الخسائر المالية.
- مسؤول تسعير: التكلفة واعتماد السعر والمستندات المالية، دون التحكم بالإنتاج.
- مدير معمل: المستخدمون والإعدادات والبيانات الأساسية والصلاحيات، دون اعتماد الطلبات تلقائيًا.

لكل شخصية يجب اختبار القائمة، الرابط المباشر، API، المرفقات، الطباعة، والعودة بالمتصفح بعد تبديل الطلبات.

## 4. فحص تسريب البيانات

- التأكد أن فاتورة الزبون لا تحتوي تكلفة فعلية أو ربحية أو خسائر تعويض.
- التأكد أن التقارير التشغيلية لا تعيد الحقول المالية لغير المخول.
- التأكد أن خطة القص وDXF لا يظهران عبر API أو رابط مباشر دون صلاحية المستند.
- التأكد أن المستخدم غير المسند لا يستطيع بدء أو تسليم مرحلة عامل آخر.
- التأكد أن تصدير الصلاحيات لا يحتوي مستخدمين أو كلمات مرور أو Session IDs.
- تجربة الطلبات الملغاة والتاريخية والـRevisions لمنع تعديل سجل قديم.

## 5. استيراد وتصدير الصلاحيات

- تصدير دور معروف ثم استيراده إلى دور اختبار مختلف.
- التحقق من Version وChecksum ورفض الملف المعدل يدويًا.
- التأكد أن الاستيراد يعرض Preview فقط ولا يحفظ قبل الضغط على زر الحفظ والتأكيد.
- عدم اعتبار قوالب الصلاحيات منحًا تلقائيًا؛ هي نقطة بداية اختيارية فقط.

## 6. خطة الرجوع

عند ظهور خلل يمنع العمل:

1. إيقاف إدخال الطلبات الجديدة مؤقتًا على الموقع المتأثر.
2. إعادة Image وCommit المسجلين قبل النشر.
3. استعادة قاعدة البيانات والملفات من النسخة المختبرة عند وجود تغيير بيانات غير متوافق.
4. تشغيل `migrate` وClear Cache على الإصدار المرجوع إليه فقط إذا كانت خطة الإصدار السابق تتطلب ذلك.
5. التحقق من الطلبات النشطة والمراحل المسندة قبل إعادة فتح الموقع.
6. توثيق سبب الرجوع وعدم إعادة المحاولة قبل إضافة اختبار يمنع تكرار الخطأ.

## 7. قرار الإطلاق

يتم تحويل الـPR من Draft فقط عندما تتحقق جميع الشروط التالية:

- Static Checks خضراء على الرأس النهائي.
- Frappe v16 Integration خضراء على الرأس النهائي.
- التثبيت النظيف و`migrate` مرتين ناجحان.
- جميع اختبارات الشخصيات ناجحة على موقع Develop مستقل.
- لا توجد Role Gates ثابتة أو APIs غير محمية.
- تمت مراجعة العربية، الموبايل، التمرير، حالات التحميل، ورسائل الأخطاء.
- تم تسجيل موافقة المستخدم بعد اختباره الفعلي.

بعد الدمج المعتمد فقط يمكن استخدام مسار النشر المعتاد مثل `update-almdina` على البيئة المحددة، مع مراقبة السجلات والطلبات النشطة مباشرة بعد النشر.

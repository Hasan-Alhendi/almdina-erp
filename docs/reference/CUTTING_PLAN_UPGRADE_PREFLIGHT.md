# Cutting Plan upgrade preflight (isolated site only)

## Change contract

Goal: preserve verifiable manufacturing plans across code upgrades without
accepting changed execution inputs. This change covers versioned readers,
new-plan V4 evidence, read-only inventory and a preflight comparison. It does
not migrate or repair existing plans, alter approved snapshots, change roles,
run the optimizer for recovery, or write to a production site. No new UI text or
capability is introduced. Rollback risk: an older release cannot interpret V4
plans created after this release; roll back code only after checking those plans
on a restored copy and arranging a compatible reader.

## Contract boundaries

| Category | Evidence and policy |
| --- | --- |
| Manufacturing inputs | Board dimensions and the free-text board material description (the only active material specification), effective cut and finished dimensions, physical quantity, rotation permission, per-side machining and edge thickness, special shape, glass, doubles, source identity, machine, kerf and preferred trim are bound in V4. Saved sheets, placements, rotations, physical execution and OFFCUT allocation remain in the immutable plan snapshot and must pass their existing validation/export checks. |
| Layout | The plan's saved sheets and imported DXF are not regenerated by compatibility reads. V4 separately hashes the saved sheets and requires successful saved validation; a damaged or changed layout needs review. Export's detailed geometry/kerf checks still apply. |
| Optimizer provenance | Search time, optimization mode, engine version and order revision are recorded by their existing fields/trace. The new snapshot also records `generation_input_fingerprint`. They do not invalidate an already saved physical layout by themselves. |
| Commercial data | Costs, rates, customer details and notes are excluded from V4. The board description can specify the physical material and is therefore included. V1 hashed some metadata and is read only for history. |
| Lifecycle | Only the order-linked Approved revision can support new manufacturing; Draft is a candidate for review, while Cancelled and Superseded stay historical. A persisted stale flag still blocks new execution. |

V1 and the three known V2 shapes (Git parents `13c3c89c`, `e8453978`)
and V3 keep their original hash semantics. The frozen historical piece reader
does not call the current optimizer adapter. The V3 golden corpus and its
independent checksum remain unchanged. V4 uses the same reviewed physical
piece projection, excludes order revision and optimizer search settings, and
captures the exact V4 payload in the newly created snapshot. Its SHA must
match both that captured payload and the current physical inputs. An unknown
contract, damaged baseline, or insufficient older evidence requires review;
none of these outcomes mutates an approved plan during a read.

Changing a legacy order's revision alone during a verified save does not
cancel its approval when the full V4 input projection before and after that
save is equal. That transient comparison does **not** make its old SHA a new
durable proof: subsequent manufacturing remains blocked if the old hash cannot
be verified. A real manufacturing input change retains the cancellation path.
No `PERSISTED_STALE` flag is cleared by this change: its cause was not recorded
and a value could have changed and then reverted.

## Inventory and preflight

Run on a recent **isolated restored site**, with its DXF files restored and
bench environment active. The audit uses document read permission and plan
capabilities; use an account with complete site visibility for a full-site
inventory. It never calls a write API. Its manifest contains order and plan
identifiers but no customer details; protect it as operational data.

```sh
python scripts/plan_upgrade_preflight.py manifest --site isolated.example --output /secure/before.json
# Switch the isolated bench app checkout to the proposed commit, migrate the
# isolated copy if required, and run the same command into /secure/after.json.
python scripts/plan_upgrade_preflight.py manifest --site isolated.example --output /secure/after.json
python scripts/plan_upgrade_preflight.py compare --before /secure/before.json --after /secure/after.json
```

The comparison exits 0 only for `PASS`; all other outcomes exit 2.
`BLOCKED_BY_REGRESSION` means a previously eligible plan lost eligibility or
its required DXF became unavailable. `REVIEW_REQUIRED` covers changed
classifications/lifecycle, missing/new plan rows, incomplete manifests, or
unchecked DXF files. The current Develop does not yet emit this manifest
schema, so the first rollout must treat its old audit as an incomplete
baseline and review the isolated site's cases manually; it cannot claim an
automatic PASS retroactively. Future upgrades should capture both manifests
with this schema before any production deployment. Do not run the manifest
command on the live site as part of this rollout.

The Bench summary entry point is
`almdina_erp.almdina_erp.services.cutting_plan_fingerprint_audit.audit_cutting_plan_summary`.
The streaming inventory accepts `order_names`, `page_size` (1–500) and
`verify_files`. It keeps only one page and the current draft names for one
order in memory. It distinguishes `lifecycle_candidate`,
`fingerprint_compatible` and plan-level `manufacturing_authorized`; shop-floor
capability, assignment and stage authorization still apply separately.
Uploaded DXF checks require a private File attached to the exact plan and an
accessible disk path. `NOT_CHECKED` never counts as manufacturing authorized.

## Recovery decision and rollout

For legacy plans, compare authorized Version records, approval/cancellation
events, the original immutable snapshot, its File attachment and pre-change
backups on the isolated copy. Do not infer an edit from an unmatched SHA.
If full physical inputs, placement, machining, kerf, trim and OFFCUT source
can be proven, an administrator may design a **new** Draft revision from the
verified saved geometry, run the existing geometry and export validations,
then request explicit approval with current capabilities. Do not change the
Cancelled/Superseded source, its DXF, fingerprint, snapshot or approval log.
No automatic recovery command is supplied because historical snapshots may
lack the required machining proof; unknown cases require human review.

Before rollout: back up DB and DXF files, test restoration, audit the isolated
copy, compare classifications with the proposed code, inspect authorized real
examples and investigate every regression. Deploy gradually only after
explicit acceptance; audit again after rollout. A code rollback to a release
without a V4 reader cannot safely operate V4 plans created in the interim.
